# Migrating from upstream Huly

`migrate-from-huly.sh` moves a Docker Compose install of upstream Huly
([`hcengineering/huly-selfhost`](https://github.com/hcengineering/huly-selfhost), v0.7.x) to
this repository **in place**. Your data stays where it is. The script reuses the Docker
project (`DOCKER_NAME`) and its volumes, and switches the images from `hardcoreeng/*` to
`platformcollective/*`. On first start, the platform's own migrations bring the workspaces up
to this version.

For a v0.6 (MongoDB) install, follow the
[v0.7.204 section of MIGRATION.md](../MIGRATION.md#v07204) instead. The script detects such
an install and refuses to run.

## Steps

```bash
git clone https://github.com/Platform-Collective/platform-selfhost.git
cd platform-selfhost

# 1. See what will happen (nothing is changed)
./migrate-from-huly.sh /path/to/huly-selfhost --dry-run

# 2. Migrate: back up, stop Huly, start from this folder
./migrate-from-huly.sh /path/to/huly-selfhost
```

Run it in a fresh checkout. The Huly folder is never modified.

## What is carried over

Your changes are worked out against the pristine upstream files (`migration/huly-v0.7.426`).
Anything you changed is carried over on top of this repository's versions.

| In the Huly folder | Here |
|---|---|
| `huly_v7.conf`: host, SSL, ports, title, language, volume paths, `DOCKER_NAME` | `huly_v7.conf` (regenerated by `setup.sh`). Relative volume paths become absolute |
| Secrets (`.huly.secret`, `.cr.secret`, `.rp.secret`, or the values in the config) | the same files |
| Variables that this repository's template does not have (e.g. SMTP credentials) | `custom.conf`, which `setup.sh` appends to the config on every run |
| Your changes to `compose.yml`: added services (mail, love, github, ...), changed environment, ports, limits, removed services | `compose.override.yml`, with images switched to `platformcollective/*:${HULY_VERSION}` |
| Files that added services bind-mount (`./livekit.yaml`) | copied here. Directories (data) are referenced at their old path |
| Your changes to `.huly.nginx`: uncommented locations, your own locations, changed directives | merged into this repository's `.huly.nginx`. Your original is kept as `.huly.nginx.huly-orig` |
| `nginx.conf` (host nginx) | copied as is. Re-point your `sites-enabled` link at the new path |

Keep your own changes in `compose.override.yml` and `custom.conf` from now on. Then
`git pull` never conflicts with them.

### Conflicts

If you and this repository changed the same setting, for example `FRONT_URL` of `transactor`,
the script stops and lists the conflicts. Rerun it with one of these options:

- `--on-conflict=ours` keeps this repository's value.
- `--on-conflict=theirs` keeps your value.

## Rolling back

The database schema is upgraded on first start, so rolling back needs the backup. The
backup is taken right before the switch and restored from the Huly folder.
`migration-report.md` has the exact commands:

```bash
cd platform-selfhost && docker compose down
cp restore.sh /path/to/huly-selfhost/ && cd /path/to/huly-selfhost && ./restore.sh <backup> --yes
```

## Options

| Option | |
|---|---|
| `--dry-run` | Only print the plan and stage the files in `.migration/stage` |
| `--yes` | Do not ask for confirmation |
| `--skip-backup` | Do not run `backup.sh` first (then you have no rollback) |
| `--on-conflict=stop\|ours\|theirs` | See [Conflicts](#conflicts) |

## Testing

CI (`.github/workflows/migrate-from-huly.yaml`) runs three kinds of checks:

- the planner tests in `tests/migration`;
- a check that every upstream image has a published counterpart;
- an end-to-end run: upstream Huly is installed with typical changes, data is created and
  migrated, the data is checked, and the install is rolled back to Huly.
